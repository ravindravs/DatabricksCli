BOTTLENECK ANALYSIS: WHAT BREAKS FIRST AT EACH SCALE
================================================================================

BOTTLENECK #1: LLM API RATE LIMITS (PRIMARY)
────────────────────────────────────────────────────────────────────────────
Constraint: OpenAI (200K TPM) limits you to ~1,500 forms/day
At 10,000 forms/day: EXCEED OpenAI limit by 6.7x

Solution: Use Claude batch APIs (50% cheaper) + real-time hybrid approach
- Batch processing: 8-24 hour latency, $0.08/form
- Real-time: < 5 second latency, $0.15/form
- Blended: $0.06-0.08/form (vs $0.50 for GPT-4 only)

Cost Impact: $5,000-15,000/month
Alternative: AWS Bedrock provisioned throughput ($4,500/month unlimited TPM)

Status at Each Scale:
├─ 100 forms/day: No constraint (use free OpenAI tier)
├─ 500 forms/day: Monitor (approaching limit)
├─ 1,000 forms/day: Use batch APIs (optimize cost)
├─ 5,000 forms/day: Blend batch + real-time (manage cost)
└─ 10,000 forms/day: Use Bedrock or multi-region OpenAI

BOTTLENECK #2: PDF GENERATION (SECONDARY)
────────────────────────────────────────────────────────────────────────────
Constraint: Sequential PDF generation, memory-intensive

Capacity by Tool:
├─ PDFKit (Node.js): ~500 forms/day (Vercel compatible)
├─ Lambda: ~300,000 forms/day (with proper concurrency)
├─ ECS Fargate: ~500,000 forms/day
└─ AWS Bedrock Titan: Unlimited

Solution: SQS queue + Lambda auto-scaling (handles 100K+ PDFs/day easily)
Cost Impact: $100-500/month
Optimization: PDF caching (80% hit rate) saves $200-500/month

Status at Each Scale:
├─ 100 forms/day: In-process generation (PDFKit in Lambda)
├─ 500 forms/day: Add SQS queue, Lambda concurrency 10-20
├─ 1,000 forms/day: Increase Lambda concurrency to 50
└─ 10,000 forms/day: Lambda concurrent limit = 1,000 (more than sufficient)

BOTTLENECK #3: DATABASE I/O (TERTIARY)
────────────────────────────────────────────────────────────────────────────
Constraint: RDS instance IOPS (Input/Output operations per second)

Capacity by Instance:
├─ db.t3.micro: ~50 forms/day (free tier)
├─ db.t4g.small: ~500 forms/day
├─ db.r6g.large: ~2,000 forms/day
└─ db.r6g.2xlarge: ~5,000+ forms/day

Solution: Add read replicas, implement indexing, use RDS Proxy
Cost Impact: $100-600/month per replica
Optimization: Database indexing alone = 10x faster queries (free)

Status at Each Scale:
├─ 100 forms/day: db.t3.micro (free tier), no replicas
├─ 500 forms/day: db.t4g.small + RDS Proxy
├─ 1,000 forms/day: db.t4g.small + 1 read replica
├─ 5,000 forms/day: db.r6g.large + 2 read replicas
└─ 10,000 forms/day: db.r6g.2xlarge + 3 read replicas

BOTTLENECK #4: CONCURRENT USERS (SECONDARY)
────────────────────────────────────────────────────────────────────────────
Constraint: Database connection limits

Capacity:
├─ Vercel: 100-200 concurrent users
├─ Lambda: 1,000 concurrent users
└─ ECS: 10,000+ concurrent users

Solution: Connection pooling (RDS Proxy), auto-scaling
Cost Impact: $30-100/month
Typical workload: 15 minutes per form, so 1,000 forms/day = ~6-12 concurrent users

Status: Not a concern until 5,000+ forms/day

- Cost: $2,000

TRIGGER FOR PHASE 2 → PHASE 3 MIGRATION:
- When: 2,000 forms/day consistently for 1 week
- Symptoms:
  ├─ Database CPU > 80%
  ├─ Lambda concurrency limit hit
  ├─ OpenAI TPM limit exceeded
  └─ P99 latency > 8 seconds
- Effort: 50-60 hours
- Downtime: < 30 minutes
- Cost: $3,000

COST OPTIMIZATION PRIORITIES (by ROI):
1. LLM API optimization (use batch): Saves 60-80% = $5-15K/month
2. Database indexing (free): 10x faster queries, enables smaller instances
3. PDF caching (Redis): 80% hit rate, saves 40% on PDF generation
4. Connection pooling (RDS Proxy): Reduces database CPU by 30%
5. CloudFront caching: Reduces origin requests by 80%
