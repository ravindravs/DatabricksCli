KEY SECURITY DECISIONS
================================================================================

1. ENCRYPTION AT REST
   ├─ Client-Side (Primary)
   │  ├─ AES-256-GCM encryption before data leaves browser/app
   │  ├─ Key derivation: PBKDF2-SHA256 (600K iterations)
   │  └─ User password-based key (never transmitted)
   │
   ├─ Server-Side (Defense in Depth)
   │  ├─ Application-layer re-encryption (redundant)
   │  ├─ Database-level encryption (PostgreSQL pgcrypto)
   │  ├─ Master key in AWS Secrets Manager + KMS
   │  └─ Quarterly key rotation (automatic, transparent)
   │
   └─ Net Result: Server cannot decrypt user data without user password
       (even if database is compromised, encrypted blobs are unreadable)

2. ENCRYPTION IN TRANSIT
   ├─ Mandatory TLS 1.3 (TLS 1.2 acceptable for legacy clients)
   ├─ HSTS header (63072000 seconds = 2 years)
   ├─ Certificate pinning for mobile apps
   ├─ No plaintext HTTP (all redirects to HTTPS)
   └─ Net Result: Man-in-the-middle attacks prevented

3. ZERO-KNOWLEDGE ARCHITECTURE
   ├─ Client generates commitments (SHA-256 hashes + range proofs)
   ├─ Server validates proofs WITHOUT decrypting data
   ├─ Use case: Form validation (SSN format, date ranges, consistency)
   ├─ Example: Prove "SSN is 9 digits" without revealing SSN value
   ├─ Library options: libzk.js or SEAL (C++/WASM)
   │
   ├─ When to use ZK:
   │  ✓ Form validation
   │  ✓ Multi-form consistency checks
   │  ✓ Risk assessment (cross-field validation)
   │
   └─ When NOT to use ZK:
      ✗ PDF auto-fill (must decrypt to populate)
      ✗ Authentication (requires plaintext comparison)
      ✗ Real-time validation feedback (too slow, ~100ms per proof)

4. LLM API SECURITY (CRITICAL - Claude/OpenAI Risk)
   ├─ PROBLEM: Claude/OpenAI have data retention policies
   │           Sending raw PII violates security + compliance
   │
   ├─ SOLUTION: Redaction Proxy Pattern
   │  ├─ Architecture: Isolated microservice (AWS Lambda/ECS Fargate)
   │  ├─ Input: Encrypted form data (from main service)
   │  ├─ Process: Decrypt → Redact → Call LLM → Extract insights
   │  ├─ Output: Insights only (no PII returned to user)
   │  └─ Logging: Never logs plaintext (redacted only)
   │
   ├─ Redaction Rules (Tier 1 Data)
   │  ├─ SSN: Send only "ssn_valid: true/false" + length validation
   │  ├─ Passport: Send only "passport_valid: true/false"
   │  ├─ DoB: Send only "age_over_18: true/false"
   │  ├─ Address: Send only "[REDACTED]"
   │  └─ Visa Status: Send only visa category code, not full details
   │
   ├─ Example Safe LLM Call:
   │  POST /api/analyze {
   │    form_type: "I-130",
   │    ssn_valid: true,
   │    passport_valid: true,
   │    visa_status: "F-1",
   │    inconsistencies_detected: ["employment_dates_overlap"],
   │    missing_fields: ["employment_start_date"]
   │  }
   │
   └─ Net Result: Claude/OpenAI never sees raw PII, cannot retain data

5. KEY MANAGEMENT
   ├─ Master Key: AWS Secrets Manager + KMS
   │  ├─ Encrypted at rest (KMS key)
   │  ├─ MFA required to access from code
   │  ├─ Automatic rotation (quarterly)
   │  └─ Audit log (CloudTrail) of all access
   │
   ├─ User Keys: Derived from password in browser
   │  ├─ Never transmitted to server
   │  ├─ Never stored in database
   │  ├─ Erased from memory after encryption
   │  └─ Lost if password forgotten (design choice: no recovery)
   │
   └─ API Keys (OpenAI/Claude)
      ├─ Stored in Secrets Manager (not environment variables)
      ├─ Separate key per environment (dev/staging/prod)
      ├─ Quarterly rotation
      └─ Scoped to specific endpoints if provider supports

6. ACCESS CONTROL (Zero-Trust)
   ├─ Employee Access
   │  ├─ MFA required for all accounts
   │  ├─ VPN required for database access
   │  ├─ Role-based (Admin/Support/Analyst/Read-Only)
   │  ├─ Admin tier requires 2 MFA methods + manager approval
   │  └─ Automatic lockout after 30 days inactivity
   │
   ├─ Database Access
   │  ├─ Application layer only (no direct DB access)
   │  ├─ Row-level security (users see only own data)
   │  ├─ No queries with SELECT * (explicit column selection)
   │  └─ Read-only queries logged for auditing
   │
   └─ API Access
      ├─ OAuth2 (Google/Microsoft login) for users
      ├─ JWT tokens (15-minute expiry + 7-day refresh)
      ├─ Rate limiting (100 req/min per IP, 1000/hour per user)
      └─ Request signing (HMAC-SHA256) for sensitive operations

7. LOGGING & MONITORING (No PII)
   ├─ Structured JSON logs (not plain text)
   ├─ Never log: SSN, passport, passwords, plaintext PII, API keys
   ├─ Always hash: user_id (use HMAC, not plain)
   ├─ Retention: 7 years (encrypted storage)
   ├─ Alerts: Failed decryption (>5/min), unauthorized DB access, key usage anomaly
   └─ SIEM: ELK stack or Datadog + CloudWatch

8. BACKUP & DISASTER RECOVERY
   ├─ Daily automated backups (RDS automated backups)
   ├─ Point-in-time recovery (35 days)
   ├─ Cross-region replication (geo-redundancy)
   ├─ RTO (Recovery Time Objective): < 1 hour
   ├─ RPO (Recovery Point Objective): < 15 minutes
   ├─ Monthly restore testing (verify backups work)
   └─ All backups encrypted (AWS native encryption)

CRITICAL "DO NOT" LIST
================================================================================

❌ NEVER
  • Log plaintext SSN, passport, or any Tier 1 PII
  • Send unencrypted PII to LLM APIs (Claude, OpenAI)
  • Store encryption keys in environment variables
  • Commit API keys or secrets to Git (use Secrets Manager)
  • Use HTTP (always enforce HTTPS)
  • Trust client-side validation alone (server-side required too)
  • Store user passwords (hash only, using bcrypt cost 12+)
  • Grant database access without VPN + MFA
  • Disable CORS for "security" (use proper auth instead)
  • Skip penetration testing before launch
  • Assume "security through obscurity" works
